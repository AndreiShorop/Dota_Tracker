Dota Tracker v0.1.0

Dota Tracker is a professional desktop analytics application for Dota 2. It provides a PySide6 UI backed by PostgreSQL to ingest data from OpenDota, persist it reliably, and deliver analytics and visualizations for players, matches, heroes, and items.

Status: Foundation layers (Phase 0) complete. GUI implementation is deferred until Phases 0–3 are complete.

Core goals

  • Clean Architecture with dependencies pointing inward: Presentation → Application → Domain; Infrastructure implements Application ports.
  • GUI never blocks — API calls run in QThreadPool workers via QRunnable, emitting signals back to the GUI thread.
  • OpenDota rate limit (~60 req/min unauthenticated) mitigated with a token bucket limiter, exponential backoff with jitter, and optional API key.
  • No hardcoded secrets — configuration via pydantic-settings from environment variables / .env.
  • PostgreSQL with tables players, matches, heroes, items, player_matches using JSONB for flexible API response storage.

Clean Architecture Domain → Application → Presentation

Dota Tracker follows Clean Architecture (ports and adapters) so business logic stays independent of frameworks, UI, database engines, and external APIs.

Layers

LayerResponsibilities
Domain Core entities (Player, Match, Hero, Item, PlayerMatch), value objects, domain services, business rules, repository interfaces. Pure Python — no I/O, SQLAlchemy, HTTP, or Qt.
Application Use cases (e.g. sync player matches), port definitions (OpenDotaGateway, UnitOfWork), DTOs, orchestration. Depends on domain only.
Infrastructure Adapters implementing ports: SQLAlchemy repositories, Alembic migrations, OpenDota HTTP client, pydantic-settings config, loguru logging.
Presentation PySide6 UI, views, view models. Depends on application use cases/DTOs only — no direct DB or HTTP logic.
Analytics Metrics, aggregations, pandas/numpy computation, matplotlib visualizations consuming domain/application outputs.

Dependency rule

Presentation  -->  Application  -->  Domain
                         ^                 ^
                         |                 |
                    Analytics      Infrastructure (adapters)

Inner layers must not import from outer layers. Domain has no framework dependencies; infrastructure never leaks SQLAlchemy/Qt types across port boundaries.

Ports and adapters

  • Ports are interfaces/protocols defined by the application layer (e.g. "fetch match by id", "persist player matches").
  • Driving adapters (primary): UI controllers invoking use cases.
  • Driven adapters (secondary): PostgreSQL repositories, OpenDota gateway, cache, clock.

OpenDota API Integration

The integration lives in the infrastructure layer behind the OpenDotaGateway application port, keeping domain/application logic independent of HTTP and provider details.

Components

  • OpenDotaClient — low-level sync HTTP client on httpx.Client: base URL, auth params, timeouts, retries, rate limiting.
  • OpenDotaGateway — adapter implementing the application port. Operations: get_player(account_id), get_player_recent_matches(), get_match(match_id), get_heroes(), get_items().
  • Response models — Pydantic v2 models for OpenDota payloads (extra fields tolerated for drift), with mappers to application DTOs.
  • Endpoint registry — centralized path builders (/players/{id}, /players/{id}/matches, /matches/{id}, /heroes, /items).

Rate limiting

  • Token bucket / sliding window limiter — acquire a permit before each request.
  • Concurrency cap via semaphore for async batch fetches.
  • On HTTP 429, respect Retry-After when present; otherwise exponential backoff with jitter.
  • Shared limiter across gateway methods to prevent accidental bursts.

Retry logic

  • Retryable: network errors, 429, 500/502/503/504.
  • Non-retryable (fail fast): 400/401/403/404/422 and validation failures.
  • Exponential backoff with jitter (base 0.5s, max 30s); bounded by OPENDOTA_MAX_RETRIES.

Sync vs async

ScenarioPreferred
Single player/match fetch from UISync (httpx.Client)
Bulk historical sync (many matches/players)Async (bounded concurrency)
Periodic scheduled syncSync or Async (idempotent jobs)

Configuration

  • OPENDOTA_BASE_URL, OPENDOTA_API_KEY (optional), OPENDOTA_TIMEOUT_SECONDS, OPENDOTA_MAX_RETRIES, OPENDOTA_RATE_LIMIT_RPM.
  • Never hardcode API keys; validate settings at startup; redact secrets from logs.

Key indexes & constraints

    uq_players_account_id, uq_matches_match_id, uq_heroes_hero_id, uq_items_item_id
  • uq_player_matches_match_player_slot (match_id, player_slot)
  • Partial index on player_matches(account_id) WHERE account_id IS NOT NULL
  • Check constraints: non-negative kills/deaths/assists, player_slot 0–127
  • Indexes on start_time, game_mode, patch, player_id, hero_id, match_id + is_radiant

Relationships

  • players 1:N player_matches
  • matches 1:N player_matches
  • heroes 1:N player_matches
  • items 1:N player_matches (7 item slots)
  • Up to 10 player_matches rows per standard match

Schema is evolved exclusively through Alembic migrations (initial migration: 0001_initial_schema). Raw JSONB payloads are stored selectively for traceability.
